# 移动管理 App 首版设计

日期：2026-10-03（北京时间）

状态：用户于 2026-10-03 确认开始，设计已批准；实施计划审阅完成前不开始产品代码实现。

## 1. 目标与成功标准

恢复 `registration_system_admin_app/` 的 Flutter 管理客户端，为赛事运营人员提供手机上的日常运营完整流程。用户已选择登录、工作台、比赛与报名管理、球队与成员管理作为首版范围，并要求首版整体考虑架构、分层、UI 和交互质量。

参考现有 Go 网页管理端的业务语义、权限、字段和表单规则，按移动操作场景重新组织页面。首版交付 Android/iOS 工程、可执行验证和使用说明；交付标准是主要流程可用且失败路径明确，而非只有页面入口或静态样板。

功能完整性以本文的范围表和验收清单为准。实现期间允许分批完成与验证，但首版交付前须完成全部约定流程。代码签名、商店发布和生产数据操作不属于本次开发交付。

## 2. 已核实的现状与技术选择

- 当前 App 目录仅有 `AGENTS.md`；历史提交 `02d0626` 保留 Flutter Android/iOS 工程和登录、创建比赛、创建球队等早期代码。
- 历史请求层使用 Rust 的 `/api/admin`、`/activities`、`/teams/admin` 和 `{ success, message, data }`；历史管理员状态类型也与 Go 不同。不得直接复用为新客户端的业务实现。
- Go 管理接口为 `/api/v1/admin`，统一响应 `{ code, message, data }`，成功 `code = 0`；登录返回 Bearer token，没有已核实的管理员 refresh-token 路由。
- Flutter/Dart 工具链和 iPhone 模拟器可用。Android 构建工具、iOS 原生依赖和签名需在实施时检查。

选择 Flutter 原生客户端：保留现有技术方向和平台工程身份，复用可核实的平台配置，替换旧协议及业务页面。相比包裹网页，可明确控制移动导航、键盘和表单反馈；相比更换移动技术栈，可减少工程与维护面。

状态管理使用 Flutter 的 `ChangeNotifier`/`Listenable` 和构造函数依赖注入。每个 feature 有独立 controller 和不可变状态，不使用全局万能 store；请求使用可注入的 HTTP transport。敏感会话通过封装的系统安全存储适配器保存，普通偏好单独存储。原生安全存储插件需在实施时核对平台要求、锁定依赖并验证构建。

## 3. 首版功能与边界

| 模块 | 首版交付 | 对应协议 |
| --- | --- | --- |
| 会话 | 登录、恢复并验证会话、登录过期统一处理、退出、账号信息 | `POST /auth/login`、`GET /auth/me` |
| 工作台 | 近期比赛入口、创建比赛/球队快捷操作、服务连接状态 | 比赛查询；独立根路径 `/health` |

| 比赛详情 | 基本信息、报名分组、名单、报名状态、占用人数和支付状态 | `GET /matches/:id` |
| 比赛操作 | 开始、结束、取消；进行中/结束后录入或修正比分；超管删除 | `PATCH /matches/:id/status`、`PATCH /matches/:id/score`、`DELETE /matches/:id` |
| 球队 | 列表与状态筛选、本地名称搜索、创建/编辑、详情、入队密码设置/清除、按权限删除 | `/teams`、`/teams/:id`、`/teams/:id/join-password` |

上表除 `/health` 外的路径均相对 `/api/v1/admin`。表内简写必须在 repository 中使用完整实际路由。

报名管理首版为网页管理端已有的花名册查询和状态展示，不提供代用户报名、修改个人报名状态或签到。球队约战申请选择/撤回虽然已有 Go 路由，但不属于本首版范围。用户列表、管理员列表、权限配置、小程序审核、提示内容、系统设置、比赛队费结算、钱包管理也留到后续。

创建比赛沿用网页当前提供的三种模式：线下已约、线上约球队、线上约散人。对已有 `online_pickup` 比赛支持查看及后端允许的编辑，创建入口不擅自开放网页尚未开放的散人约球/收费配置。编辑不修改发布模式或主队，不覆盖未暴露的收费字段。

工作台展示真实比赛数据和快捷入口；没有汇总接口的统计不展示为全量业务指标。

## 4. 架构与依赖方向

```text
lib/
  app/                         # 启动装配、会话门禁、路由、底部导航
  core/
    network/                   # transport、统一响应、超时与错误分类
    storage/                   # 安全会话/普通偏好/待确认队费请求适配器
    time/                      # 北京时间、UTC 时刻、纯日期
    money/                     # 元分转换和校验
  design_system/
    tokens/                    # 色彩、字号、间距、圆角、状态语义
    theme/                     # 深浅 ThemeData 与统一控件主题
    widgets/                   # 页面骨架、表单分区、异步状态、确认等
  features/
    session/
    dashboard/
    matches/
    teams/
    members/
    team_fund/
    account/
      domain/                  # 不可变模型、规则、repository 契约
      data/                    # DTO、映射、HTTP repository 实现
      application/             # controller、状态、表单编排和操作协调
      presentation/            # 页面和领域内组件
```

目录按实际职责建立；简单 feature 可以合并同职责的小文件，不机械填满每一层。

- `domain` 不依赖 Flutter、HTTP 或存储插件；`application` 只使用模型、repository 契约及必要的 Listenable 状态机制。
- `data` 实现领域契约，集中处理 JSON 与请求协议。页面不直接解析 JSON、不拼 URL、不维护 Bearer token。
- `presentation` 消费 controller 的只读状态并发出意图，不承担接口适配和资金规则。
- `app` 是依赖装配入口，处理跨 feature 的会话和导航；领域之间通过明确方法/刷新事件协作，不互相 import 私有页面状态。
- 控制器、transport 和订阅明确释放；页面销毁后不写状态，异步回调不使用失效 context。
- 文件按变化原因划分；接近 600 行评估相关职责拆分，避免大页面同时承载网络、表单、权限和响应组装。

列表使用统一异步状态模型：首次加载、成功空列表、已有数据刷新、首次失败、局部操作失败。保留上次成功数据的状态必须标记刷新失败，不能让旧数据显示为操作成功后的最新结果。

## 5. 接口契约、权限与会话

服务环境由构建配置注入；release 默认使用当前 jd 的 HTTPS API base。base 与 `/api/v1/admin` 前缀分别处理，支持反向代理子路径，禁止重复追加前缀。健康检查不使用管理前缀。release 不提供随意填写服务器的输入框；环境切换只对开发构建开放并清理会话、导航和缓存。

启动依次读取环境与安全 token，然后请求 `/auth/me`：有效会话进入主界面；401 清空本地会话并进入登录；网络失败保留 token，展示重试，不误判账号失效。登录密码不持久化。日志不输出 token、密码、真实连接串或完整个人信息。

任一受保护请求收到 401，由会话协调器执行一次清理，关闭所有受保护页面和弹窗，清空该账号缓存并回登录。并发 401 不重复导航；旧请求完成后不得恢复已退出账号的数据。管理员切换使用 session generation 防止前一会话的回调污染新会话。

403 保留当前会话并展示无权限；404 展示资源不存在并允许返回；业务校验错误保留表单并显示原因。网络错误、超时、非 JSON 响应、业务 code 非零分别归一化为可展示错误。

接口模型显式表达数字 ID、字符串 UUID、枚举、可空字段和金额整数。未知展示枚举可降级为“未知状态”，不得因此开放操作；关键字段错误应明确提示数据格式问题。

权限以 Go application/service 和 middleware 为权威。比赛删除仅超管可用；当前球队维护（含删除）、成员与队长管理、人工队费动作允许已登录管理员。客户端按已知权限展示操作，后端拒绝仍作为最终判断。队长任免走专用 captain 接口，不通过普通角色更新绕过限制。

## 6. 比赛与成员的关键数据规则

- 比赛列表后端分页；修改搜索或状态后从第一页查询。以请求代次隔离过期响应，同一页不并发重复加载；刷新重新建立分页状态，结果按 ID 去重。
- 球队列表是数组接口，名称搜索为本地过滤；候选成员搜索调用已有候选接口，选择必须来自结果，不要求运营手工输入 user ID。
- 比赛状态操作按当前状态提供；比分范围沿用当前规则 `0–999` 的整数，`0` 与尚未录入的 `null` 分开显示。
- 比赛表单按基本信息、赛程和报名、场地、其他选项分区。业务模式限制、字段长度、人数、时长、经纬度、颜色及报名窗口使用独立规则模块，与实际 Go 校验及网页行为核对。
- DTO 区分缺省、不修改、显式清空。报名时间编辑的省略与 `null` 含义、球服颜色和对手名称的空字符串清除语义必须保留；地图坐标未修改时保留原值。
- 新建成功进入真实详情；编辑成功刷新详情和列表；成员操作成功刷新成员信息、球队人数与相关队长信息。操作失败保留输入且不得提前修改列表为成功态。
- 名单人数按 `registration_count` 累计，不能简单以行数当人数。未报名、请假、缺席、取消等状态分别展示；人数摘要使用明确状态口径，不将全体花名册人数当已报名人数。
- 普通成员编辑与队长任免分离；队长不可通过普通移除动作绕过后端规则。付费会员标记只提交 `is_paid_member`，不提交已废弃的余额/充值时间字段。

## 7. 时间与资金规则

遵循根目录 `docs/time-handling.md`。

具体时刻解析为 UTC，旧无时区接口值显式按 UTC 解析。展示和日期选择使用北京时间的年月日时分，不依赖 `DateTime.now()` 的宿主本地分量或 `toLocal()`。表单使用独立北京时间挂钟值对象；提交明确转换为 UTC RFC3339。纯日期 `received_on` 始终为 `YYYY-MM-DD`，不通过 UTC 时刻转换。

金额从字符串十进制规则转换为整数分，不用浮点乘 100 再截断；最多两位小数，必须大于零，当前单笔充值/消费上限为 1,000,000 分（10,000 元），与 Go `maxManualAmountCents` 保持一致。负余额按欠款展示。充值是登记实际线下收款，消费扣费和冲正分别说明作用；不提供直接编辑余额的输入。

每次人工队费动作首次提交前生成并保存 idempotency key 和原请求，按服务环境、管理员、球队、成员和动作隔离。持久化成功后才发请求；禁用重复提交。成功或明确未执行的业务校验拒绝后清理待确认请求；网络中断、超时、5xx、无法解析响应或中途登录过期保留原 key 与原 payload，展示“结果待确认”，允许显式以原请求重试，禁止重新生成 key 或修改同一待确认请求的金额。无法判断是否执行的错误一律保留待确认状态。

App 重启或重新登录同一管理员后可恢复待确认动作；退出清除 token 和业务缓存，不将待确认动作暴露给其他账号。待确认请求由安全存储适配器保存并按账号隔离，界面不自动重放。服务返回 `duplicated` 也按成功确认，随后刷新余额和流水。

创建比赛、添加成员等未核实幂等的写请求不自动重试。若网络中断导致结果不确定，提示刷新检查后再决定操作。

冲正从具体流水进入，展示原金额、说明和影响，仅对后端支持且未冲正的人工流水开放；必填原因，提交时携带原流水 ID。操作后展示新流水和最终余额，不删除历史。

## 8. 移动 UI 设计

整体采用运营工具的清晰层级：中性工作表面、青绿主操作色、独立状态语义色。深色为初始主题，提供浅色并持久化偏好。主题、字号、间距、圆角和控件尺寸集中定义，业务页面不逐个定义视觉常量。

底部导航为“工作台 / 比赛 / 球队 / 我的”。切换保留各 tab 的筛选和滚动位置；详情、编辑及长表单是二级页面。返回顺序明确：关闭当前浮层、返回详情/列表、再退出应用；退出会话重建受保护路由栈。

列表使用信息卡片/行，而非横向挤压桌面表格。比赛突出名称、状态、北京时间、场地与对阵；球队突出名称、状态、成员数与队长；成员突出姓名、角色、会员状态与余额。次要信息进入详情。高风险动作放“更多”并带确认，主要操作保持可见。

正文约 16 logical px，辅助信息 13–14，页面标题约 22；点击热区至少 48，页面边距按 16/20 刻度，输入和按钮共用主题。圆角以控件 8、面板 12 为基准，不堆叠发光、渐变或装饰性卡片。颜色和图标不可作为状态的唯一表达。

表单固定底部操作区避开安全区和键盘，不遮挡最后字段；键盘 next/done 顺序合理。长名单或筛选用适合单手操作的 sheet，复杂编辑使用整页。可滚动内容支持长文本和空头像降级，不出现横向溢出。

## 9. 交互与错误恢复

- 首次加载显示占位；下拉刷新保留内容；空状态区分“没有数据”和“筛选无结果”，提供创建或清除筛选入口。
- 搜索防抖、后提交请求优先；筛选变化重置分页；加载更多失败可在底部重试，不抹掉已加载内容。
- 表单校验紧邻字段，提交时定位首个错误；提交中按钮显示进度并锁定重复提交；成功提示后刷新真实数据。
- 新建/编辑表单有 dirty 检测，返回或切换页面前提示未保存内容；失败保留所有输入。会话失效不得绕过登录继续提交。
- 删除、取消、移除成员、任免队长、充值/扣费和冲正的确认内容含具体对象及影响；取消确认不产生网络请求。
- 下游操作已成功但刷新失败，明确显示“操作成功，数据刷新失败”及重试，不能引导再次执行写操作。
- 网络失败可重试读取；写操作按上一节的不确定结果规则处理。所有请求有超时，长耗时操作不无限等待。
- 错误反馈由统一组件展示，避免同一请求同时重复弹 toast 和阻塞弹窗；账号失效使用全局反馈，字段错误留在表单。

## 10. 验证与交付门槛

### 可自动验证的行为

HTTP mock 验证 URL/前缀、Bearer、`code = 0`、数组与可空返回、HTTP/业务错误、401/403、超时及非 JSON。repository 验证 Go DTO 类型和清空语义。控制器验证会话隔离、请求竞态、分页重置、防重复提交和成功后的刷新。

共享时间工具覆盖跨日/跨年、UTC 与无时区输入、北京时间挂钟转 UTC、纯日期。金额工具覆盖两位小数、非法格式、零/负数、上限及精确分值。资金流程验证同 key 重试、pending 恢复、不同账号隔离、duplicated 响应和冲正。

Widget 测试覆盖登录、关键列表空/错/加载状态、表单字段错误、返回保护、权限隐藏和资金确认；不新增仅断言颜色/样式字符串的测试。使用假 repository/transport 验证，不向线上业务表写测试数据。

### 构建与人工验收

- `dart format lib test`、`flutter analyze`、`flutter test`。
- `flutter build apk --debug`；具备工具链时 `flutter build ios --simulator`。
- iPhone 模拟器检查关键路径，并保留深浅主题截图；Android 模拟器/真机可用时补充平台验证。
- 布局覆盖 360/390/430 宽度、横屏、安全区、键盘、长名称、空头像、长错误、文本放大至 2 倍；必要时调节操作布局而非截断关键内容。
- 无凭据时使用测试 fixture 的独立 harness 展示 loading/empty/error/success，不将模拟模式和假数据接入 release。
- 未跑的环境/构建/真实接口验收写明原因，不能用静态检查通过代替真机或生产接口验收。

### 首版验收清单

1. 同一管理员可完成登录→创建球队→添加/维护成员→创建/编辑比赛→查看报名→开始/录入比分/结束。
2. 查询、取消、删除等权限和状态限制与后端一致；未授权操作不假成功。
3. 可完成会员标记、收款登记、扣费、流水查看和合法冲正；重复点击和超时重试不重复记账。
4. 退出或登录过期后，嵌套页面不可再访问旧数据；再次登录不受旧响应污染。
5. 首次失败、无数据、筛选无结果、刷新失败、提交失败都有具体恢复路径。
6. 所有页面使用共享主题与组件；页面、应用状态、协议和业务规则边界可从目录与依赖直接辨认。
7. Android/iOS 工程恢复，锁定依赖；说明配置、开发运行、构建、验证和首版边界。
8. 根目录及 App 的 `AGENTS.md`、`README.md` 在实施时同步更新开发状态，删除过时 Rust 接口说明。

## 11. 实施约束与审阅结论

仅恢复移动管理客户端和相应文档，不恢复 Rust/旧 Vue 项目，不调整现有 Go API 和数据库 schema。发现真实接口不足时先记录具体阻塞与影响，不能编造接口或借移动端任务扩大后端改造范围。

后续实施计划按基础工程与设计系统、会话、比赛、球队与成员、队费、整体验收拆分；每一部分明确文件边界和验证，再集成为上述完整首版。

自审结论：范围已明确；历史协议差异、报名管理边界、创建模式、时区、权限和队费不确定结果均已定义。环境依赖的构建及真实账号验收有明确报告要求。用户已确认进入实施计划阶段。
