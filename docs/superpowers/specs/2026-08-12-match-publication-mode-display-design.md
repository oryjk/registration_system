# 比赛发布模式跨端展示设计

## 目标

Go 后端创建比赛支持三种 `publication_mode`：

| 后端值 | 展示文案 | 含义 |
| --- | --- | --- |
| `offline_confirmed` | 线下已约 | 已在线下确定对手，不需要线上招募 |
| `online_team` | 线上约队 | 在线招募一支球队作为对手 |
| `online_individual` | 散人对手 | 在线招募个人组成对手阵容 |

管理端和小程序必须使用同一组语义，在创建时可明确选择，在浏览和详情中可快速识别。类型是比赛核心元信息，但不应挤占报名、签到或状态操作区域。

## 展示位置

### React 管理端

- 创建比赛：将现有“发布模式”改为更直观的“比赛类型”，保留三种选项，并为每种选项提供一句简短说明。编辑时类型保持只读，符合后端当前不支持修改发布模式的契约。
- 比赛列表：在比赛名称下方以紧凑标签显示类型。该位置与名称同属身份信息，桌面和窄屏都能保留，不新增独立列。
- 比赛详情：在标题下方的状态信息行中以标签显示类型；详情描述区增加“比赛类型”字段，便于明确核对。

### uni-app 小程序

- 发布比赛：用三项分段选择替换旧的“对外友谊赛 / 队内内战”二选一，直接对应后端三种 `publication_mode`。只有“线下已约”显示对手名称输入；另外两种不提交 `opponent_name`。
- 首页与比赛列表：类型标签放在比赛标题附近，与比赛阶段标签并列。用户扫列表时能先判断比赛性质，不占用报名进度和操作按钮区域。
- 我的比赛：复用同一类型映射，在标题下的元信息行显示类型标签。
- 比赛详情：在首屏比赛标题/状态附近显示类型标签，并在基础信息中保留明确的“比赛类型”项。

## 数据与模块边界

- 管理端列表和详情 DTO 已包含 `publication_mode`，只补充统一展示组件或映射，不改变请求结构。
- 小程序普通比赛列表和详情 DTO 已包含 `publication_mode`；首页聚合 DTO 当前未包含该字段，因此 Go 后端首页 action/ended 响应补充 `publication_mode`，并同步 OpenAPI、handler 测试和小程序类型。
- 小程序建立单一的发布模式类型及文案映射，创建 payload、列表视图模型和详情展示共同引用，避免页面各自维护字符串。
- 不修改 Rust 后端，不引入新的数据库字段或迁移。

## 交互与兼容

- 类型值未知时，页面使用“其他类型”作为只读兜底，避免接口扩展导致空白；创建端仍只允许后端当前三种合法值。
- 切换小程序创建类型时清理不适用的对手名称，确保 `online_team` 和 `online_individual` 不会触发后端“不能填写手工对手名称”的校验。
- 保持现有页面视觉语言：管理端使用 Ant Design `Tag` 和选择控件；小程序沿用现有紧凑标签与分段控件样式，不重做页面布局。

## 验证

- Go：补充首页响应映射测试，执行相关 Go 测试，并按仓库要求执行 `go test -race ./...`、`go vet ./...` 和构建。
- React 管理端：执行 `bun run type-check`、`bun run lint`、`bun run build`，检查列表、详情和创建页的桌面及移动视口。
- 小程序：补充发布 payload 和视图模型的关键映射测试，执行 `bun run type-check`、相关测试和 `bun run build:mp-weixin`，检查首页、我的比赛、详情和发布页。
