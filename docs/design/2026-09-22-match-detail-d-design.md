# 比赛详情页 D 风格设计与实现交接

2026-09-22。用户要求：减少详情页冗余信息和无必要文案，用图标与紧凑排版提高可读性，保持首页已验收卡片的设计标准。本文是统一改版计划任务 5 的详情页实施依据；实现由用户指定 Agent 执行，当前对话负责 review，用户负责双端界面测试。不启动额外任务，不改后端。

## 1. 目标与当前事实

用户进入详情应能迅速回答：什么比赛、何时何地、费用如何、谁参加、我现在能做什么。沿用薄荷蓝/海军蓝、轻描边、语义状态色和公共动效；详情页为静态纵向页面，不复制首页叠卡。

已读当前代码：`src/pages/matches/detail.vue` 经 `MatchIndividualRegistration` 编排 `IndividualMatchupHero`、`MatchRegistrationStatusCard`、`TeamMemberRegistrationBoard`、`IndividualInfoCard`；页面另有联系队长、编辑、申请、结束/取消和比分组件。下文路径均相对 `registration_system_mini/`。

| 当前问题 | 本批处理 |
| --- | --- |
| 页面固定标题“比赛报名”，结束/取消后仍一样 | 导航统一为“比赛详情”；比赛阶段用概览内的小徽章表达 |
| 大日期块、48rpx 标题、独立球服行占高度 | 标题与性质徽章同行，时间改横排；球服并入对应球队旁 |
| 已报人数在大数字、进度文案、头像标题重复 | 一个报名摘要行、一条对应进度；名单计数只保留在筛选项 |
| 状态卡头像与队员状态板重复 | 同一报名组只渲染一处名单；球队场景保留状态分组能力 |
| 队员状态板重复“队员状态/已报名/我的状态/已报名” | 保留一次名单标题、一次分段筛选；个人状态放行动栏 |
| 概览和 MatchScoreCard 重复比分 | 比分在对阵区显示一次；管理员录入/修改放管理入口 |
| 编辑、联系、结束比赛各自大卡和解释段落 | 联系改紧凑行；编辑/比分/结束/取消集中管理区 |
| 空说明自动写入“迟到 10 分钟视为请假”“雨天提前 1 小时通知”等 | 删除未经发布者填写的默认规则，不把模板当真实赛事规则 |
| `currentTeam?.creditScore ?? 0` 被标成“本场比赛信用” | 取消这个错误归属的展示；它是当前身份球队的值，不能冒充本场或主办方信用。保留球队原有信用数据和其他页面功能，不新增信用接口 |

只换图标和颜色不能解决上述问题。采用信息合并和明确主次；不采用“所有内容塞进一张大卡”或“所有操作藏到更多里”。

## 2. 页面结构与排版

页面顺序：比赛概览 → 报名摘要与名单 → 比赛说明（有内容才展示）→ 联系队长（沿用现有显示条件）→ 管理区域（有权限才展示）。底部仅一个个人行动栏；进行中/结束/取消普通用户无报名行动栏。

示意为虚构数据，仅说明排版；`[图标名]` 实现时使用图标，不渲染方括号文字：

```text
‹                       比赛详情

周二长远友谊赛  [队内报名]              [报名中]
[clock] 09/22 周二 20:00–22:00
[map-pin] 长远体育公园                        ›
[users] 8 人制     [wallet] ¥25/人 · 赛前支付

[队徽] 东安洛悦   VS   长远联队 [队徽]
       [球衣色块]            [球衣色块]
─────────────────────────────────────────────
已报名 7 / 最多 12 人                 还差 1 人成行
━━━━━━黄色进度━━━━│────剩余────

参赛名单
已报名 7      请假 2      未报名 3
头像+姓名  头像+姓名  头像+姓名        展开全部 ›

比赛说明
发布者真实填写的内容……                 展开

[队长头像] 队长昵称                       联系队长
─────────────────────────────────────────────
仅有权限时：比赛管理
修改比赛    录入比分    接约申请 2
结束比赛                         取消比赛（危险色）

固定底栏（示例）
[circle-check] 已报名                  [修改状态]
```

- 内容边距 24rpx，概览内边距 26/28rpx，模块间 20–24rpx；使用已定义 token。不要每个信息行再套卡片、粗边框或小标题。
- 标题 34rpx/600，自然换行；正文 24–26rpx，次要信息 22rpx，徽章 20–24rpx。时间不再使用首页 68rpx 大字。
- 时间一行、地点一行、人制和费用同一横向信息组；长地点、长金额自然换行，不用固定高度裁掉。保留起止时间；跨日时显示结束日期，不能只显示两个钟点造成误解。
- 对阵只占一组紧凑布局。队徽、队名和球衣色保持对应；可用小号“主/客”帮助定位，删除独立“主队球服/客队球服”行。长队名允许换行。颜色只有真实值时才显示，并保留白色球衣的可见边线。
- `online_pickup` 无主队，不创建虚假的“主队 VS 客队”；隐藏不适用的对阵模块，保留真实比赛名、人数、费用等。
- 真实比分在对阵中央替换 VS；任一比分未知不补 0；`0:0` 是有效比分。取消比赛明确标“已取消”，不能混成已完成。时间已过但服务端尚未结束，可显示“时间已过”，管理员看到“待确认结束”，不宣称已有最终结果。

## 3. 图标与文案规则

图标用于替代字段名，保留字段值；不会要求用户猜测图标代表什么动作。

| 信息 | 展示 | 省略的重复文字 |
| --- | --- | --- |
| 时间 | `clock` + 日期、星期、起止时间 | “比赛时间：” |
| 地点 | `map-pin` + 地点；有效坐标时带轻箭头 | “比赛地点：”“点击查看地图” |
| 人制 | `users` + “8 人制” | “比赛人数：” |
| 费用 | `wallet` + “免费”/“¥25/人 · 赛前支付”/“赛后结算”/“费用待确认” | 单独“费用说明”卡、重复金额 |
| 个人状态 | `circle-check`/`user-round-minus`/`clock` 等 + “已报名/已请假/待支付/未报名” | “我的报名”“我的状态”“已选中” |
| 比赛性质 | 标题旁短徽章 | 说明区再次展示“比赛类型：…” |
| 联系、管理、支付、报名、取消 | 图标可辅助，必须保留动作文字 | 删除“比赛信息有变化？”“可修改比赛时间、对手与报名人数”等入口教学句 |

- 优先复用 `src/static/icons/lucide/` 现有 PNG：clock、map-pin、users、wallet、circle-check 等。新增必要图标按现有 SVG+PNG+LICENSE 方式维护，不引入仅 H5 可用的图标库。
- 返回、关闭可用纯图标，但须有可访问名称与足够热区。装饰图标不重复朗读；不能只靠颜色区别状态。
- 位置无坐标时保留地点文字，隐藏可导航箭头，不伪装成可打开地图的链接。
- 保留真实业务警告和确认文案：支付取消会保留报名、取消后改为请假、已支付不可调整、二次确认等，不作为“冗余”删掉。

## 4. 报名摘要、名单与个人状态

### 报名摘要

- 单报名组显示一次“已报名 N / 最多 M 人”，旁边显示“还差 X 人成行”或“已成行”。无上限时显示“已报名 N 人 · 人数不限”，不能用最低人数或人制冒充上限；门槛未知则不显示达标结论。
- 延用首页语义：未达最低人数为黄色；达标段薄荷色；超出门槛段海军蓝；门槛分隔点可见。不要再叠加“报名进度”“成行 / 满员”“满员 M 人”三组标题。人数等于上限才标满员，最多人数不是当前满员状态。
- 报名开始/截止信息仅显示一次，靠近行动区域；保留原始报名窗口计算，不新增高频计时器。不把尚未开放误写成“报名已结束”。
- 主客队组各保留自己的报名摘要与人数，不能合并统计或挪用另一组的最大/最小人数。需要组切换时保留明确队名；当前用户所属组优先，其他组可查看。

### 名单

- 同一组只保留一个名单区域。球队组用“已报名 N / 请假 N / 未报名 N”分段选择，不再重复当前分组标题和计数；默认选择沿用当前行为，不借 UI 调整改变状态。
- 默认展示最多 8 个紧凑“头像+姓名”条目，可用两列；超过时“展开全部（N）/收起”。完整名单不丢失，长姓名换行；点击仍可查看完整姓名及“我”标识。无头像保留姓名首字回退。
- 散人名单不伪造球队全员及未报名名单。`registration_count > 1` 显示“姓名 · 共 N 人”，不能把账号数量当参赛人数；数据无该值时不得猜代报名人数。
- 当头像预览与成员分组并非同一个报名组，先查清数据归属再合并，不能只为去重删除独有参与者。
- 展开保持当前阅读位置，使用局部平滑过渡；大量条目避免全列表依次动画。减少动态效果时直接切换或短淡入。

### 个人行动栏

由页面/展示 composable 仲裁一次，子卡不各自挂 StickyActionBar。状态在左、一个主动作在右；并存的必要次动作采用轻量文字入口。下表描述展示优先级，实际资格及提交仍沿用现有判定和 handler。

| 场景 | 状态与动作 |
| --- | --- |
| 游客且报名可用 | 登录后报名，进入原登录路径；不把游客标成已报名 |
| 非比赛球队成员且无开放散人组 | 加入球队后报名，保留原加入/密码/联系队长流程 |
| 未报名/请假且窗口开放、有名额 | 状态徽章 + 报名；球队的请假选择继续可达 |
| 球队成员已报名 | “已报名”+“修改状态”，沿用状态确认弹窗；不把整条栏染成危险红 |
| 散人已报名、未支付且允许修改 | “已报 N 人”+“调整人数”；保留原取消入口与条件 |
| 报名费待支付 | “待支付 · ¥总额”+“去支付”；可调整人数时给次入口。金额是总额，概览的单价仍保留 |
| 散人已支付 | 显示“已报名 · 已支付”，不暗示可以改人数或取消；遵守当前锁定规则 |
| 未开放/截止/满员 | 紧凑状态与原因，不能显示看似可报名的大按钮；已报名用户是否仍可修改按原规则，不用满员统一禁掉 |
| 进行中/结束/取消普通用户 | 查看比赛和名单，没有报名/取消报名/修改人数栏；真实待支付费用按下述独立规则处理 |

**支付不因视觉只读被误删：** 当前 `pendingPaymentFeeLabel` 独立于报名窗口。对进行中/结束等状态，仅移除修改参赛状态的入口；如既有支付逻辑仍允许支付，保留独立紧凑费用行和“去支付”，不把它伪装成报名主按钮，不新增支付资格判断或退款规则。若认为终态应禁止支付，属于另行产品决策，本批不得自行处理。独立账单页的结算功能保留。

## 5. 说明与管理区

- 比赛说明仅渲染 `description` 的真实内容。空值直接省略整个区块；短说明完整显示，长说明默认四行，提供展开/收起并保证完整内容可达。这里不再次列类型、人制、时间、地点。
- 删除默认迟到/天气/爽约文案以及错误的“本场比赛信用”标签；不修改 API 字段和存储数据。
- 联系队长为头像、姓名、“联系队长”的紧凑行，继续使用 `captainContactCaptain` 的既有身份判断、留言弹窗及消息流程。
- 比赛管理仅依照 `canEditMatch`、`canManageApplications`、`canFinishMatch`、`canCancelMatch`、`matchScore.canRecordScore` 展示。合并布局，不合并或重写权限判断。
- 修改比赛、录入/修改比分用轻量入口；取消保持危险语义和二次确认。结束比赛不需要再次在入口段落复述完整比赛名/结束时间，确认弹窗保留必要说明。
- 接约申请有待处理项时默认展开，保留申请球队、简介、状态和“选为对手”；没有申请可显示“暂无申请”，去掉宣传式长句。已有已选/婉拒/撤回记录仍可查看。
- 管理员同时是参赛者时，个人行动栏与管理区域分开，不能让“结束比赛/取消比赛”替代自己的报名操作。

## 6. 数据与组件实施约束

| 设计信息 | 当前可信来源/接线 |
| --- | --- |
| 名称、性质、人制、起止时间、费用、地点、球衣色、比分 | `sourceMatch: AppMatchSummary` 与现有 `match` 适配模型；费用读取 `is_free/payment_mode/fee_per_person_cents`，未知不能当免费；不把 `creditScore` 解释为本场数据 |
| 当前报名组 | `detailData.ts` 的既有组选取、`AppMatchDetailResponse.groups`；必须按身份与组 ID 匹配，不能取数组第一项 |
| 人数、最少/最多 | 对应组 `attending_count/min_players/max_players`；展示可以补透传真实字段，但不得改现有提交上限计算。当前 `maxPlayers` 有回退计算，不能将回退值表述成后端设置的容量 |
| 状态/个人份数/支付 | `currentStatus/myRegistrationCount/myRegistrationPaid/pendingPaymentFeeLabel` 与既有报名窗口、登录和资格判定 |
| 比赛阶段 | `sourceMatch.status/start_time/end_time`；核对首页现有 `resolveMatchPhase`，需要复用时抽取纯工具，不复制一套互相矛盾的时间规则。展示阶段与服务端终态不能混称 |
| 动作 | 原 `handleSelectIndividualSignup/handleSelectTeamMemberStand/handlePayRegistration` 及编辑、比分、结束、取消、申请 handler |

- 首选调整现有职责：`IndividualMatchupHero` 做概览；`MatchRegistrationStatusCard` 做摘要；`TeamMemberRegistrationBoard` 做名单；`IndividualInfoCard/MatchInfoCard` 做真实说明；`MatchIndividualRegistration` 做展示编排。不强制趁本批重新命名业务组件。
- 新的行动展示状态可抽到 `matchDetailPresentation.ts` 或 `useMatchDetailPresentation.ts`，依赖显式输入、输出展示信息和动作类型；不要在模板中堆条件或在展示函数内请求 API。先搜索已有工具，能复用就不新增重复实现。
- 可以添加纯展示 props、移动既有事件接线；所有调用方同步，保留事件语义和提交数据。不删除共享组件的兼容接口，详情使用方不需要的装饰通过可选项关闭。
- `detail.vue` 已较长，不继续堆入状态机。当前文件结尾 `.match-edit-*` 规则在 `</style>` 之外，调整编辑区域时移入有效样式块或所属子组件。
- AppSurface 用 `flush` + 自己模板内 wrapper 承载布局；不依赖父 scoped `custom-class` 穿透小程序组件隔离。
- 不修改后端/接口/导航路由；本批不操作生产报名、支付、取消等数据。不引入 Web-only DOM 或动画库。
- 弹层使用第 3 步修复后的公共进退场机制；关闭动画期间遮罩拦截、滚动锁定和防重复提交一致，快速反向/卸载清理可靠；不要复制目前自制弹层缺少退场的模式。

## 7. 给实现 Agent 的工作顺序与验收

1. 第 3 步 P2 修复通过后开始。先提交详情展示状态与组件数据来源清单，重点核对报名组、真实容量、阶段与支付资格。
2. 改概览、合并重复人数/名单/比分，去除未经发布者填写的规则和错误信用归属；保留全部独有信息和操作。
3. 收敛个人行动栏，集中管理区域；详情状态变化只影响展示，仍调用既有 handlers。不要借机改创建页 payload、报名规则或其他页面流程。
4. 补局部展开/切换/点击动效和 H5 减少动态效果，验证小程序宿主节点布局。既有首页叠卡不调整。
5. 交付 diff、自动验证结果及以下人工验收清单，再交 reviewer；不自行提交/发布。

用户 H5 + 微信端验收：

- 队内、球队约队、散人对手、散人约局；游客、普通队员、非成员、主/客队管理者；管理员兼参赛者。
- 未报名、请假、已报名、代报多人、待支付、已支付；免费、赛前支付、赛后结算、费用未知。
- 未开放、开放、截止、满员、进行中、时间已过未收尾、已结束、已取消；缺少上限/门槛、最低等于最高、主客队容量不同。
- 无比分、0:0、已录入比分；普通用户只读和管理员比分入口不重复。
- 无说明/长说明、长名称/场地、无定位、空名单/100 人名单、无头像、加载/失败；无需遍历无限长头像才能找到主动作。
- 首屏能辨认比赛与自己的状态；同一字段仅在必要语境重复（概览单价与支付总价、各组人数不算重复）；全页只有一个个人固定行动栏。
- 窄屏、H5 宽屏、键盘与安全区不遮挡操作；展开无明显跳动，切换不串组，弹层关闭不点穿，减少动态效果有效。

Review gate：精简信息而不丢功能；未知数据不被包装成确定信息；普通用户的查看态与管理动作区分明确；费用/权限/请求不退化，双端编译及组件注册通过。截图与真实手势验收由用户完成。
